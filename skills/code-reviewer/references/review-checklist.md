# Review checklist

Prompts for what to examine, grouped by area. Use the areas the diff touches. A finding still needs a concrete consequence; a checklist item alone is not a finding.

## Contents
1. Correctness
2. Security
3. Data and migrations
4. API contract
5. Frontend
6. Tests
7. Performance
8. Maintainability

## 1. Correctness
- Does each acceptance criterion and edge-case row in the task have code that implements it?
- Boundaries: off-by-one in limits, empty lists, `None` / `null` / `undefined`, zero, negative numbers.
- Branches: is every `if` and `else` reachable and correct? Are early returns skipping necessary work (audit logs, cleanup)?
- State transitions follow the rules in the data model (an Order cannot go from Cancelled to Pending).
- Concurrency: two requests at once (double submit, two tabs) cause duplicates or lost updates? Unique constraints or row locks where it matters.
- Time: time zones, naive datetimes, end-of-month, DST.
- Changed function signatures or return values: do unchanged callers still work? (A named-risk check outside the diff.)
- Errors are handled where they can be handled, and propagated otherwise. No empty catch blocks, no catch that only logs and continues as if nothing happened, no fallback to fake data.
- Async: no blocking calls (sync DB drivers, `requests`, `time.sleep`, heavy CPU) inside `async def`; awaited promises; no fire-and-forget without error handling.

## 2. Security
- Authentication required on every non-public endpoint and Server Action.
- Authorization at the object level: queries scoped by owner or tenant (`WHERE user_id = :current`), not filtered after fetching.
- Input validated at the boundary (Pydantic schemas, Zod in Server Actions), with lengths and ranges from the contract.
- Mass assignment: request bodies mapped to explicit fields, not `Model(**body)` with arbitrary keys (`role`, `is_admin`, `owner_id`).
- No raw SQL built with string formatting; parameters only.
- No secrets in code, logs, error messages, or `NEXT_PUBLIC_` variables; secret modules import `server-only`.
- Error responses do not leak internals: no `str(e)`, stack traces, SQL, file paths, or echoed rejected input.
- Cookies: `httpOnly`, `SameSite=Lax`, `Secure` when `ENVIRONMENT=production`; server-side sessions stored hashed and revoked on sign-out and password change; no tokens in `localStorage`.
- Test-only routes (seed, fault injection) registered only when `ENVIRONMENT == "test"`, never gated on "not production".
- CORS: none in the default same-origin setup (browser calls relative `/api` through the Next.js rewrite); where added, never wildcard origins with credentials.
- Money in API responses is a `{amount, currency}` object with integer minor units.
- Redirects go to allow-listed destinations only.
- `dangerouslySetInnerHTML` only with sanitized content.
- Server-side requests to user-supplied URLs (webhooks, link previews) are allow-listed and time-limited.
- File uploads: size and type limits enforced on the server, stored outside the web root, never executed.

## 3. Data and migrations
- Migration matches the data model contract (names, types, nullability, constraints).
- Autogenerated migrations reviewed: enum changes, server defaults, and index changes are often missed or wrong.
- Foreign keys indexed; columns used in `WHERE`, `ORDER BY`, and joins on hot paths indexed.
- Destructive changes (drop column, add NOT NULL, rename) are safe for the code that may still be running: add first, backfill, switch code, remove later.
- Backfills batched; no full-table rewrite on a large table in one transaction.
- `downgrade()` exists and works, or the irreversibility is stated.
- Only one migration head (no forked revision chains from parallel tasks).
- Money in integer minor units or `NUMERIC`, never float. Timestamps `timestamptz`.

## 4. API contract
- Paths, methods, status codes, and auth requirements match `openapi.yaml`.
- Response field names, types, nullability, and enums match exactly. No extra fields leaking internal data (password hashes, internal flags).
- Errors use the standard envelope and the contract's error codes.
- Pagination, filtering, and sorting follow the conventions.
- Breaking changes to a contract have a decision record and notified consumers.

## 5. Frontend
- Server Components by default; `"use client"` only where interactivity needs it, and as low in the tree as possible.
- Only serializable props passed from Server to Client Components.
- Every route segment that loads data has loading, error, and not-found handling; every data view has loading, empty, and error states.
- Data access through the typed API client, not ad hoc `fetch` with hand-written URLs.
- No server state duplicated into client stores; no derived data stored as state.
- Forms: labeled inputs, validation messages tied to fields, disabled or idempotent submit while pending.
- Accessibility: semantic elements (button, not clickable div), accessible names, visible focus, keyboard reachable dialogs and menus, alt text.
- Design tokens used instead of hard-coded colors and spacing.
- No hydration hazards: `Date.now()`, random values, or browser-only APIs during server render.
- Auth checks in the data layer, not only in middleware.

## 6. Tests
- Each acceptance criterion has a test; each failure path named in the task has a test.
- Tests assert outcomes (response body, DB row, rendered text), not that a mock was called.
- Expected values derived by hand, not by calling the code under test.
- Integration tests use a real Postgres when the app does.
- No tests deleted, skipped, or loosened without a stated reason.
- No sleeps or time-based waits; no dependence on test order or shared data.

## 7. Performance
Only where it matters for a realistic workload:
- N+1 queries in list endpoints or list pages.
- Unbounded queries (no limit) on tables that grow.
- Loading whole tables or large files into memory.
- Missing indexes for the query pattern added.
- Large client bundles from heavy libraries imported in Client Components.
- Expensive work repeated on every render or request when it could be computed once.

## 8. Maintainability
Only when it will plausibly cause a real problem:
- Duplicated business logic that will drift (the same rule implemented in two places).
- Hidden coupling: a module reaching into another's internals against the architecture's dependency direction.
- Names that mislead about what the code does.
- Dead code, commented-out code, debug output left in.
- New dependency added where an existing one does the job.
