# Default consistency conventions

Copy these into the project's `architecture.md` (Conventions section) and change only what the project needs. Every engineer agent reads the project copy, not this file.

## Naming

| Thing | Convention | Example |
|---|---|---|
| API paths | lowercase, plural nouns, kebab-case, under `/api` | `/api/order-items/{id}` |
| JSON fields | snake_case | `created_at`, `next_cursor` |
| DB tables | snake_case, plural | `order_items` |
| DB columns | snake_case; FKs `<entity>_id`; booleans `is_` or `has_` | `user_id`, `is_active` |
| Python | modules and functions snake_case, classes PascalCase | `order_service.py`, `OrderRead` |
| TypeScript | variables and functions camelCase, components and types PascalCase, files kebab-case | `order-list.tsx`, `OrderList` |
| Env vars | UPPER_SNAKE, frontend-public ones prefixed `NEXT_PUBLIC_` | `DATABASE_URL`, `API_INTERNAL_URL` |
| Pydantic schemas | `<Entity>Create`, `<Entity>Update`, `<Entity>Read` | `OrderCreate` |

JSON stays snake_case on the wire. The frontend uses generated types that match the wire format exactly; do not hand-convert case in scattered places.

## IDs
* UUIDv4 (or UUIDv7 if ordering by ID is useful) primary keys, generated by the database or backend. Exposed as strings.
* Never expose sequential integer IDs in URLs for user-owned data.

## Time
* Store `timestamptz` in UTC. API sends ISO 8601 with `Z`: `2026-10-27T08:15:00Z`.
* Every table has `created_at` and `updated_at`, set by the database or ORM, not by clients.
* Convert to the user's time zone only in the UI.

## Money
* On the wire, every money value is a `Money` object: `{"amount": 1999, "currency": "USD"}`, with `amount` an integer in minor units and `currency` an ISO 4217 code. Never floats, never a bare number, never a flat `total_amount` field in API responses (the database may store two columns; the schema exposes `total: Money`).

## Errors
All non-2xx responses use one shape:

```json
{
  "error": {
    "code": "order_not_cancellable",
    "message": "This order can no longer be cancelled.",
    "details": {"status": "delivered"},
    "request_id": "req_8f3a..."
  }
}
```

* `code`: stable snake_case machine code the frontend may branch on.
* `message`: safe to show to users; never includes stack traces, SQL, or internal paths.
* Validation errors (422): `details.fields` is a map from field name to a list of messages.

| Status | Use |
|---|---|
| 400 | Malformed request that is not a field validation error (bad cursor) |
| 401 | Not authenticated |
| 403 | Authenticated but not allowed |
| 404 | Not found, or exists but the user must not know it does |
| 409 | Conflict with current state (duplicate, wrong status) |
| 422 | Field validation failed |
| 429 | Rate limited |
| 500 | Unexpected; logged with request_id |

## Pagination
* Cursor-based for lists: `GET /api/orders?limit=20&cursor=<opaque>` returns `{"items": [...], "next_cursor": "..." | null}`.
* `limit` 1 to 100, default 20. Stable sort with a unique tiebreaker (for example `created_at desc, id desc`).

## Filtering and sorting
* Filters as query params named after fields: `?status=pending`. Sorting `?sort=-created_at`. Only allow-listed fields.

## Auth
* Default: email and password with **server-side sessions**. The session token is an opaque random value in an `httpOnly`, `SameSite=Lax` cookie named `botss_session` (`Secure` when `ENVIRONMENT=production`). Only a hash of the token is stored, in a `sessions` table, so sessions can be revoked on sign-out and on password change. No JWTs by default (they cannot be revoked without extra machinery), and no tokens in `localStorage`.
* Backend checks authorization on every request for every resource (ownership or role), not only in the UI.
* Passwords hashed with argon2 or bcrypt.
* CSRF protection when using cookies for mutations from the browser (SameSite plus a CSRF token or origin check).

## Browser to backend
* The browser only talks to the Next.js origin. `next.config` rewrites `/api/:path*` to `${API_INTERNAL_URL}/api/:path*`, so the session cookie is same-origin and **no CORS** is needed in the default setup. Client code calls relative `/api/...` paths.
* Server Components and Server Actions call `API_INTERNAL_URL` directly and forward the incoming `botss_session` cookie.
* CORS middleware is only added when the architecture has the browser call the API cross-origin, with an explicit origin list (never `*` with credentials).

## Environments
* `ENVIRONMENT` is `local | test | ci | production`. `test` enables e2e seed and fault-injection routes and is never used for a deployed environment. Only `production` sets `Secure` cookies.

## API behavior
* `POST` creates and returns 201 with the created resource. `PATCH` partial update returns 200 with the resource. `DELETE` returns 204.
* Idempotency key header for payment-like or duplicate-sensitive creates.
* Versioning: no URL versioning for an MVP; additive changes only, breaking changes need a decision record.

## Configuration
* All config from environment variables, loaded and validated once at startup (pydantic-settings on the backend, a validated env module on the frontend). The app fails fast with a clear message if a required variable is missing.
* `.env.example` lists every variable with a safe placeholder and a comment.

## Logging
* Structured JSON logs in production, readable logs locally. Include `request_id`, method, path, status, and duration.
* Never log passwords, tokens, full card numbers, or personal data beyond IDs.

## Frontend data access
* One typed API client module, generated from or checked against `openapi.yaml`. Components never call `fetch` with hand-written URLs.
* Server Components fetch on the server by default; Client Components only where interactivity needs it.
